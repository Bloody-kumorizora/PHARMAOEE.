# Архитектура PharmaOEE 9.0.0

## Слои

```
ui/ (Tkinter)  →  analytics, demo, sources, backup, export  →  db (все SQL)  →  SQLite
                         ↘ oee, intervals, validation (чистые функции без ввода-вывода)
```

- **oee.py** — только формулы. Ничего не обрезает и не проверяет; выход за пределы сообщает флагами.
- **validation.py** — правила допустимости ввода: ошибки блокируют сохранение, предупреждения требуют
  подтверждения. Здесь же расписание смен (`shift_for`, `shift_bounds`).
- **intervals.py** — пересечения интервалов, распределение времени без двойного учёта.
- **db.py** — единственное место с SQL. Каждый вызов открывает короткое соединение (`PRAGMA foreign_keys=ON`,
  `busy_timeout=5000`), связанные изменения выполняются в одной транзакции `BEGIN IMMEDIATE`. Режим `rw`
  не создаёт новый файл, если базы нет.
- **analytics.py** — `Snapshot`: записи периода (один запрос производства + один запрос простоев) и все
  производные показатели. Главная панель, таблицы, графики и CSV берут данные из одного снимка, поэтому
  показывают один и тот же период.
- **sources.py** — интерфейс `DataSource.poll() → list[TelemetryEvent]` для будущих интеграций,
  `validate_event` (порядок событий, будущее время для реальных источников, ошибки источника),
  `EventProcessor` (применение событий к базе), `ShiftSimulator` (демо-источник).
- **ui/** — `theme.py` (токены цвета, шрифты, стили ttk), `widgets.py` (карточки, KPI, таблица с сортировкой и
  поиском, выбор даты), `charts.py` (графики на Canvas), `dialogs.py` (формы), `views.py` и `views_service.py`
  (разделы), `app.py` (окно, навигация, общий фильтр, фоновые операции).

Длительные операции (генерация демо-данных, копирование, восстановление, проверка целостности) выполняются в
отдельном потоке со своим соединением SQLite; результат передаётся в главный поток через очередь и `after()`.

## Схема базы (версия 1, `PRAGMA user_version = 1`)

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `equipment` | справочник оборудования | `name` UNIQUE; `ideal_cycle_sec > 0`; `is_active`, `is_demo` ∈ {0,1} |
| `downtime_reasons` | справочник причин | `name` UNIQUE; системная причина «Не классифицировано» |
| `production` | записи смен | FK → equipment (RESTRICT); дата `ГГГГ-ММ-ДД`; неотрицательные значения; `source` ∈ {manual, demo, simulator} |
| `downtimes` | простои | FK → equipment; `start_at`, `end_at` (`NULL` — продолжается); `end_at >= start_at`; `source` |
| `sensor_events` | состояния от источников | FK → equipment; FK → downtimes (SET NULL); `state` ∈ {RUNNING, STOPPED, CONNECTION_LOST} |
| `change_log` | журнал создания/изменения/удаления | обычная таблица, **не** защищённый аудит-трейл |
| `app_meta` | служебные сведения (создание, миграция) | |

Индексы: по `work_date`, по (`equipment_id`, `work_date`, `shift`), по (`equipment_id`, `start_at`), по `source`.

Уникальность записи смены (дата + смена + оборудование) и имени оборудования без учёта регистра проверяется
приложением: SQLite не умеет сравнивать кириллицу без учёта регистра, а в базе v8 дубликаты допускались.

Время хранится как текст `ГГГГ-ММ-ДД ЧЧ:ММ:СС` в местном времени компьютера.

## Миграции

`Database.initialize()`:

1. версия выше поддерживаемой — отказ, база не меняется;
2. пустой файл — создание схемы;
3. база v8 (`production`, `downtimes` без `equipment`) — резервная копия в `backups/`, затем перенос в одной
   транзакции: имена линий нормализуются в справочник оборудования, ID записей сохраняются, происхождение
   определяется по пометкам v8 (демо-заметки, связь с событиями симулятора), время простоев симулятора берётся
   из точных отметок событий (в том числе после полуночи), закрытые события остановки, которые v8 перезаписывала
   как RUNNING, получают исходный тип. Проверка `foreign_key_check` перед фиксацией; при любой ошибке — откат;
4. неизвестный набор таблиц — отказ без изменений.

## Правила простоев

- Новый простой не может пересекаться с существующим простоем того же оборудования; открытый (продолжающийся)
  простой считается бесконечным.
- В аналитике пересечения из старых данных учитываются один раз: общая часть относится к простою, начавшемуся
  раньше (при равном начале — к меньшему ID). Поэтому сумма по причинам равна общему времени.
- Незавершённый простой учитывается до текущего момента; открытый дольше суток попадает в проверку данных.
- Сигнал остановки от источника открывает простой «Не классифицировано»; программа не угадывает причину.
- Потеря связи — не простой; простой, открытый до потери связи, остаётся открытым и закрывается сигналом
  «работает» с пометкой о необходимости проверки.

## Как добавить реальный источник данных

1. Реализовать класс-наследник `DataSource` с `poll()`, возвращающим `TelemetryEvent` с `simulated=False`,
   идентификатором оборудования, временем события и временем получения; ошибки связи передавать в `error`.
2. Периодически вызывать `poll()` вне главного потока интерфейса и применять события через `EventProcessor`.
3. Подключение к производственным сетям — только по отдельному техническому заданию и с разрешения владельца
   оборудования.
